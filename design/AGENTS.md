# design 目录约定

本目录用于需求、产品设计、架构设计和原型。编辑本目录内容时，除遵守根目录 `AGENTS.md` 外，还需要遵守以下规则。

# 产品设计工作边界

* 当进行产品设计工作时，包括需求分析、PRD 编写、产品方案梳理、原型设计和原型评审，只在当前 `design` 目录下收集与分析资料。
* 不要跳到上一级目录或其他目录参考前端、后端、测试、构建脚本等代码实现，除非用户明确要求进行跨目录代码分析或实现对齐。
* 产品设计判断应优先依据 `design/docs` 中的文档和 `design/prototype` 中的原型；如果信息不足，应直接说明缺口并向用户追问，而不是用代码现状补全产品结论。

# PRD / 需求文档写作规范

* 文档必须结构化编写，至少说明：背景与目标、用户对象、范围、页面/模块、核心流程、字段与规则、边界/异常情况、暂不包含、与原型的对应关系。
* 功能必须归属到具体页面、模块或流程中描述。避免只写“支持新增、编辑、删除”这类缺少上下文的功能清单。
* 原型是第一公民。PRD 中的可见页面、入口、字段、状态、按钮、弹窗、表格列、提示文案和主要交互，都应能在 `/design/prototype` 中找到对应依据。
* PRD 不得包含原型没有体现的可见功能。确实需要新增时，应先标注为“原型待补充”，并说明应该补在哪个页面或流程。
* 允许 PRD 描述原型看不见但系统必须具备的隐含功能，例如数据校验、重复判断、权限控制、持久化、日志、错误处理、导入解析、导出生成、性能约束等。
* 每个核心流程都要写边界和异常情况，包括但不限于：空数据、重复数据、非法输入、网络或服务失败、导入失败、部分成功、取消操作、删除确认、不可恢复操作。
* 当前版本范围和后续迭代必须分开写。不要把“以后可能要做”的能力写成当前版本必须实现。
* 如果文档与原型、架构或代码不一致，需要在修改时显式指出不一致点，并优先收敛范围。
